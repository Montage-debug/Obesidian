## 1. 产品定位与核心能力

### 1.1 定位

VoiceBot 是一个运行在机器人嵌入式主机（ARM/x86 Ubuntu）上的 C++ 语音助手中间件，连接：

```
物理世界（麦克风/扬声器）
        ↕
VoiceBot 中间件
        ↕
豆包 RealtimeAPI（WebSocket 流式）
        ↕
ROS2 服务 / 机械臂控制层
```

### 1.2 核心能力矩阵

| 能力模块 | 实现方案 | 备注 |
|---------|---------|------|
| 唤醒词检测 | 本地轻量 KWS（Snowboy / Sherpa-ONNX） | 离线，低功耗 |
| 多语言 ASR | 豆包端到端模型（流式实时） | 中文、方言、英/日/韩 |
| 语音合成 TTS | 豆包端到端模型（流式输出） | OGG Opus / PCM |
| 声纹识别 | 本地 Speaker Embedding + 在线比对 | 识别说话人身份 |
| 角色扮演 | SC2.0 character_manifest | 可运行时切换 |
| 声音复刻 | SC2.0 saturn_ 系列克隆音色 | 需提前注册 |
| 联网搜索 | enable_volc_websearch + location | 精准位置感知 |
| 唱歌 | enable_music（O2.0 1.2.1.1） | 版本约束 |
| 命令词控制 | ChatResponse 文本流 + 规则引擎 | 触发 ROS2 服务 |
| 静默超时 | 本地计时 + FinishSession | 可配置秒数 |
| 上下文管理 | ConversationCreate/Update/Delete | 最多 20 轮 QA |

## 5. 核心流程设计

### 5.1 唤醒 → 会话建立流程

```
[主线程] 麦克风采集 PCM 音频流（16k，int16，20ms/包）
    │
    ▼
[KWS线程] 每包经过唤醒词检测
    │ 命中唤醒词
    ▼
[SessionMgr] 状态切换 IDLE → WAKEUP
    │
    ├─ 1. 停止 KWS 检测
    ├─ 2. 播放唤醒确认音频（"我在，请说。"）
    ├─ 3. 声纹识别（可选，识别用户身份）
    ├─ 4. DoubaoWSClient::connect() 建立 WebSocket
    ├─ 5. 发送 StartConnection 事件
    ├─ 6. 等待 ConnectionStarted 事件
    ├─ 7. 构建 StartSession payload（从 config 读取全部参数）
    ├─ 8. 发送 StartSession 事件
    ├─ 9. 等待 SessionStarted 事件，获取 dialog_id
    └─ 10. 状态切换 WAKEUP → DIALOG，启动音频上传线程
```

### 5.2 对话流程（DIALOG 状态）

```
[音频上传线程]               [事件接收线程]              [音频播放线程]
    │                            │                           │
    │ 采集 PCM 20ms/包            │                           │
    │ 封装为 TaskRequest 二进制帧  │                           │
    │ ──────────────────────────▶│                           │
    │                            │ ASRInfo(首字识别)          │
    │                            │ → 打断当前播放             │
    │                            │                           │
    │                            │ ASRResponse(中间文本)      │
    │                            │ → 更新 UI/日志            │
    │                            │                           │
    │                            │ ASREnded(用户说完)         │
    │                            │                           │
    │                            │ ChatResponse(文本流)       │
    │                            │ → 送入 CmdEngine 匹配      │
    │                            │   命中命令词 → 触发 ROS2   │
    │                            │                           │
    │                            │ TTSSentenceStart           │
    │                            │ TTSResponse(音频数据)      │
    │                            │ ──────────────────────────▶
    │                            │ 推入音频播放队列            │
    │                            │                           │
    │                            │ TTSEnded                  │
    │                            │ 检查 status_code 退出意图  │
    │                            │                           │
```

#### **5.2.1 对话流程增强 (SayHello 情境感知)**

```
SayHello 结合时间与状态的实现：

- 触发时机：SessionStarted 之后，或者唤醒后的 WAKEUP 状态。
- 数据注入：
    - C++ 程序读取当前时间（2026-05-28 15:00）。
    - C++ 程序读取 ROS2 获取机械臂状态（如 Idle at Workstation A）。
    - 拼接 Prompt：将配置文件中的 say_hello_prompt 变量替换为实际值。
        - _结果_："用户唤醒了我，现在是下午3点，机械臂当前位于工位A，状态为待机。"
- 发送：发送 SayHello 事件。
- 效果：豆包模型会基于这个上下文生成一句自然的话，例如：“下午好，我准备好啦，在工位A等你指令。” 而不是生硬的“我在”。

```

#### **5.2.2 流式上下文截断 (26.02.26 新特性)**

```
问题背景：用户说话时，机器人正在播报长文本。用户想打断并追问。

- 旧逻辑：模型以为自己把话说完了，把未播放的音频内容也当成了上下文，导致理解混乱。
- 新逻辑 (ConversationTruncate)：
    1. 记录：记录当前 TTS 正在播放的 reply_id 和已播放的毫秒数 played_ms。
    2. 触发：当检测到 ASRInfo（用户开始说话）时，立即发送 ConversationTruncate 事件。
    3. Payload：{"item_id": "reply_id_xxx", "audio_end_ms": played_ms}。
    4. 结果：服务端只保留已播放的部分作为上下文，未播放的部分从模型视角“消失”。模型能正确理解用户的打断意图。

```


### 5.3 静默超时流程

```
[SilenceDetector] 独立线程，检测两种静默：

1. 唤醒后静默（WAKEUP → DIALOG 期间无语音）
   └── 超过 wakeup_timeout_s → 合成提示语 → FinishSession → IDLE

2. 对话中静默（DIALOG 期间无 ASRInfo/ASRResponse 超时）
   └── 超过 dialog_timeout_s
       ├── 合成提示语并播放
       ├── 发送 FinishSession
       ├── 收到 SessionFinished
       ├── 发送 FinishConnection（或保持 WS 复用）
       └── 重新启动 KWS 检测，状态 → IDLE
```

### 5.4 命令词控制流程

```
[ChatResponse 流式文本] 实时拼接
    │
    ▼
[CmdEngine::feedText(chunk)]
    │
    ├── 正则/关键词实时扫描（流式匹配）
    │
    │ 命中命令词
    ▼
[CmdEngine::dispatch(cmd)]
    ├─ 1. 合成并播放确认语音（ChatTTSText 事件注入）
    ├─ 2. 状态切换 DIALOG → CMD_EXEC
    ├─ 3. 调用 ROS2Bridge::callService(...)
    │      └── rclcpp::Client::async_send_request(...)
    ├─ 4. 等待 ROS2 服务响应（exec_timeout_s）
    ├─ 5. 播放执行结果语音
    └─ 6. 状态切换 CMD_EXEC → DIALOG（继续对话）
         或 CMD_EXEC → IDLE（执行完退出）
```

## 6. 命令词控制体系

### 6.1 三级匹配策略

```
优先级 高 → 低：

Level 1: 本地关键词精确匹配（极低延迟，< 1ms）
    └── "急停"、"回零" 等安全关键词，本地 trie 树匹配

Level 2: 本地正则表达式匹配（低延迟，< 5ms）
    └── "(抓取|夹取).*(物品|工件)" 等结构化命令

Level 3: LLM 意图识别（高召回，延迟与模型响应同步）
    └── ChatResponse 文本语义理解（利用豆包模型输出的自然语言）
        可在 system_role 中注入意图标签：
        "当用户想控制机械臂时，回复中必须包含 [CMD:arm_grab] 等标签"
```

### 6.2 意图标签注入（推荐机制）

在 `system_role` 中加入如下约定：

```
当用户请求以下操作时，请在回复最后追加对应标签（不影响口语化回复）：
- 抓取物品 → [CMD:arm_grab]
- 放置物品 → [CMD:arm_release]
- 回零位   → [CMD:arm_home]
- 急停     → [CMD:emergency_stop]
- 导航到XX → [CMD:navigate_to:XX]
模型正常对话，标签由系统自动剥离处理，用户不可见。
```

CmdEngine 扫描 ChatResponse 文本中的 `[CMD:xxx]` 标签，零延迟命中。

  event_id (4字节, big-endian)

## 8. 豆包 API 关键机制挖掘与建议

基于文档深入阅读，以下是值得重点利用的机制和产品建议：

### 8.1 🌟 流式上下文对齐（26.02.26 新特性）

**机制**：`ConversationTruncate` 事件支持基于客户端实际播报进度截断上下文，即只把已播放的内容告诉模型，未播完的部分不算进历史。

**价值**：用户打断播放后再追问，模型不会误以为自己说完了没说完的话，减少幻觉。

**工程实现**：
- 记录 TTSResponse 音频的累计播放时长（ms）
- 用户打断时，立即发送 `ConversationTruncate`：
  ```json
  { "item_id": "当前reply_id", "audio_end_ms": 已播放毫秒数 }
  ```
- 需要开启 `enable_conversation_truncate: true`

### 8.2 🌟 退出意图识别信号（26.03.07 新特性）

**机制**：开启 `enable_user_query_exit` 后，豆包模型感知用户说"再见/结束/拜拜"等意图，在 `TTSEnded` 事件中返回 `status_code="20000002"`。

**价值**：无需本地关键词匹配，利用模型理解自然语言退出意图，更准确。

**建议**：与本地关键词兜底双轨并行（config 中 `exit_intent` 部分已设计）。

### 8.3 🌟 音频级热修复（O2.0/SC2.0 新特性）

**机制**：服务端支持 TN 转写修正（如"3.14"正确读"三点一四"）和发音问题在线修复。

**价值**：机器人场景中涉及数字读音（如"关节角度 45.5 度"），热修复大幅提升输出自然度。

**无需额外操作**，使用 2.0 版本自动享受。

### 8.4 🌟 两遍识别（enable_asr_twopass）

**机制**：先用流式 ASR 实时返回中间文本供打断/显示，用户说完后再用非流式精修最终文本。

**价值**：机器人命令词场景中，精修后的文本用于最终命令匹配，减少误触发。

**建议**：将流式文本用于 UI 显示和快速打断检测，最终精修文本用于命令词执行。

### 8.5 🌟 ChatTTSText 主动注入（绕过模型生成）

**机制**：在收到 `ASREnded` 后、模型生成之前，客户端可以主动发送 `ChatTTSText` 注入自定义文本，服务端直接合成音频而不用模型生成。

**价值**：命令词命中后，跳过模型生成，直接注入确认语音（"好的，正在抓取"），实现 < 100ms 的极速响应。

**工程应用**：
```
ASREnded 事件
    ├── 本地命令词匹配命中 → 发送 ChatTTSText("正在执行") → 执行 ROS2
    └── 未命中 → 等待 ChatResponse（模型生成）
```

### 8.6 🌟 SayHello 主动打招呼

**机制**：会话建立后，客户端发送 `SayHello` 事件，模型主动生成问候语。

**建议**：唤醒后播放"我在"的同时，异步发送 `SayHello("用户醒来，主动打个招呼")`，让模型给出上下文相关的问候（如结合时间：早安 / 下午好）。

### 8.7 🌟 UpdateConfig 运行时热更新

**机制**：对话进行中可以通过 `UpdateConfig` 事件（201）实时更换音色、人设、地理位置。

**机器人场景应用**：
- 工位 A → 工位 B 移动时，动态更新 `location` 字段
- 切换到演示模式时，动态更换音色和 system_role，无需重启会话

### 8.8 🌟 外部 RAG 注入（ChatRAGText）

**机制**：在模型回复前注入外部知识库检索结果，模型口语化改写后输出。

**机器人场景应用**：
- 用户问"这个工件的规格是多少" → 本地数据库查询 → ChatRAGText 注入规格参数 → 模型自然语言输出
- 结合零件库、操作手册形成专业知识问答

### 8.9 🌟 多方言支持策略

文档支持：`explicit_dialect` 字段（dongbei / sichuan / shaanxi），仅 O2.0 vv 音色生效。

**更广泛方言建议**：
- 方言 ASR 识别：豆包端模型本身有一定多方言能力
- 在 `system_role` 中注入"你能理解并回复四川话/粤语"
- 对于粤语、闽南语等：可在 `hotwords` 中补充方言常用词提升识别率
- 韩语/日语：目前 O2.0 文档仅明确中英，其他语种需实测；可通过 `speaking_style` 引导模型混语回复

### 8.10 ⚠️ 重要工程注意事项

| 注意点 | 说明 |
|--------|------|
| FinishSession 必须等 ACK | 强烈推荐收到 SessionFinished 后再断 WS，否则报 ContextCanceled |
| 音频包大小 | 严格 20ms/包，16k int16 = 640 字节/包，休眠 20ms 再发下一包 |
| QPM 限流 | StartSession 每分钟不超过 60 次，注意唤醒频率 |
| keep_alive 模式 | 麦克风有静音键时务必设置，否则报 52000042 |
| ChatTTSText 时机 | 必须在收到 ASREnded 之后才能发送 |
| 克隆音色注册 | 购买后 2 分钟生效，需带音频文本提升效果 |
| SC2.0 克隆音色 | 仅对中文保障效果，其他语种暂不保证 |
